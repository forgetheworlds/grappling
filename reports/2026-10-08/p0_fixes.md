# P0 fixes: curriculum competence gates + back-to-mat ambiguity window

**Date:** 2026-10-08 · **Agent:** P0Fixes · **Scope:** `src/rl/curriculum.py`,
`src/wrestling/env.py`, plus the minimal plumbing needed to give the gate its
signal (`src/rl/reward.py`, `src/rl/rollout.py`, `src/rl/trainer.py`),
`tests/test_rl.py`, `tests/test_wrestling.py`, this report.
(`notes.md`, `src/teacher/**`, `src/scorer/**` untouched.)

Both defects came from the external engineering audit (2026-10-08) and were
confirmed against the tree before the fix. Where a claim below is a measurement,
the command that produced it is named.

---

## 1. Defect 1 — the curriculum could advance on draws alone

### 1.1 Old behaviour (measured)

`AdvanceRule(min_steps, metric="outcome_rate", threshold=0.5, window_episodes)`
with `metric = (wins + 0.5 * draws) / n`. An all-draw window (0 wins, 0 losses)
scored exactly `0.5` and cleared the inclusive threshold:

```
$ .venv/bin/python <old-code replay>            # HEAD:src/rl/curriculum.py grafted back in
old AdvanceRule fields: ['min_steps', 'metric', 'threshold', 'window_episodes']
OLD code, all-draw window: metric= 0.5  maybe_advance= True  stage= T
```

So a stage promoted on timeouts/ambiguous endings alone — zero demonstrated
success. `docs/MOTOR_CURRICULUM.md` §3 forbids exactly this ("Gates are
per-capability metrics, never exchange/outcome rate"; "Never promote because the
opponent collapses"). A further instance of the same class: `(wins, draws)`
windows were credited half per draw, so 1 win + 9 draws scored 0.55 and passed.

### 1.2 New behaviour

The rolling window now holds one `ExchangeSample` per finished exchange —
`(outcome, similarity, stood)` — and a stage advances iff **all** of:

```
steps_in_stage >= min_steps
len(window)    == window_episodes          (a full window)
successes      >= min_successes            (>= 1, enforced in __post_init__)
successes / window_episodes >= min_rate    (in (0, 1], enforced)
```

where `success` is declared **per stage** by an `AdvanceRule.criterion`:

| criterion | success means | used by |
|---|---|---|
| `"outcome"` | the learner **won** the exchange; draws (timeout, ambiguous) and losses are non-success slots | D (resistance), E (attack-vs-defense) |
| `"execution"` | the learner **held its ground** (no back-to-mat trigger against it, no OOB forfeit) **and** the attempt scored `>= min_similarity` on the technique scorer; an unmeasured attempt is *not evidence* and never counts | A, B, C (imitation/drilling) |

Because `min_successes >= 1` and `min_rate > 0` are constructor invariants
(`AdvanceRule.__post_init__` raises `ValueError` otherwise), a draw-only,
loss-only, unmeasured or low-similarity window scores `0.0` and can **never**
advance — the failure mode is now structurally impossible, not merely
discouraged.

**Why the criterion is per stage (orchestrator correction, superseding the
earlier "wins-only for A-D" instruction).** A wins-only gate *deadlocks* and
*misleads*:

* stages A-C run against `stand_hold`, which draws forever → a wins-only gate is
  unsatisfiable there (deadlock);
* the audited counterexample is the opposite failure: the stage-C smoke run
  recorded **W/L 299/0/20 while the same checkpoint stood only 13.1 % of the
  time** (external audit, as relayed by the orchestrator) — "wins" generated by a
  collapsing scripted opponent prove nothing about competence.

So A-C gate on their own objective (execution competence) and D-E on the
exchange outcome; **no stage can advance on draws/losses/unmeasured attempts**.

### 1.3 Signal plumbing (exchange → gate)

The gate's inputs exist only inside the rollout loop, so they are carried
through, in this order:

```
env step  ->  info["exchange_ended"]            (ExchangeRecord, unchanged)
          ->  StageReward.shaping(..., sample=) (new out-param: this call's scorer value)
          ->  RolloutCollector                   (per-env mean similarity attached to the
                                                  exchange record: rec["similarity"])
          ->  Trainer._absorb                    (outcome + similarity + stood/forfeit)
          ->  Curriculum.on_exchange(outcome, similarity=..., stood=...)
```

* `rec["similarity"]` is the **mean of the subsampled scorer measurements during
  that exchange**, or `None` if none was taken (no scorer / term disabled /
  learner is not the technique's executor, e.g. SPRAWL).
* `stood` = the learner has no back trigger of its own **and** did not forfeit
  via OOB. Taking the learner's own back is a fall; forfeiting is not holding
  ground either.
* `ExchangeSample`/`AdvanceRule` are checkpointed (`state_dict`, stage `as_dict`)
  and resume-exact; the runtime-only `success_hook` is deliberately excluded from
  `as_dict` (a callable cannot be checkpointed) and re-installed from config.
* `Curriculum.gate_status()` reports `criterion/window/successes/metric/
  unmeasured/min_*` so a stuck stage is diagnosable in a long run instead of
  silently stalling.

### 1.4 Attribution extension point (documented, not implemented)

`AdvanceRule.success_hook: Callable[[ExchangeSample], bool] | None` is the seam
for MISSION's later "**success attributable to the attempted technique**"
requirement. It can only *reject* a success, never manufacture one. Today only
outcome-criterion stages (D-E) need it — an outcome-criterion win is
attributable only once the attempt/technique travels with the verdict; A-C use
their scorer-based execution criterion instead. No attribution logic is
implemented now.

### 1.5 Chosen gate values — **placeholders**

| stage | criterion | min_steps | window | min_successes | min_rate | min_similarity |
|---|---|---|---|---|---|---|
| A | execution | 20 000 | 10 | 1 | 0.5 | 0.5 |
| B | execution | 30 000 | 20 | 1 | 0.5 | 0.5 |
| C | execution | 40 000 | 20 | 1 | 0.5 | 0.5 |
| D | outcome | 40 000 | 20 | 1 | 0.5 | (unused) |
| E | — (final stage, `advance=None`) | | | | | |

Rationale and honest status:

* `min_steps` / `window_episodes` are unchanged skeleton values from before this
  fix (already flagged "documented skeletons, not tuning results") — not
  re-invented here.
* `min_rate = 0.5` is the *previous* `threshold = 0.5` number, kept so the only
  difference is the semantics. The same number is now strictly harder: it is a
  pure success rate with no half credit for draws/falls, so windows that passed
  before (all draws; 1 win + 9 draws) no longer pass.
* `min_successes = 1` is the §3 floor (at least one demonstrated success), not a
  tuned value.
* `min_similarity = 0.5` is a **placeholder**. The scorer's own calibration
  (`reports/2026-10-08/scorer.md`) puts *reference* execution at roughly
  0.46-0.74 per phase, so 0.5 is mid-scale, not a measured recognition gate. It
  must be set experimentally from the scorer's held-out evidence plus the §5
  held-out protocol, and recorded with the config that produced it.
* **All** of the above are placeholders to be set by baseline-first measurement
  (`docs/MOTOR_CURRICULUM.md` §5) — none are authoritative numbers.

### 1.6 Frozen / unchanged

`ExchangeRecord`, the env observation/action/reward contract, `PerturbationSchedule`,
reward weights, opponent specs, `CommandScheduler`, and `Curriculum` checkpoint
semantics are unchanged apart from the window entry type. `metric()` now takes no
name argument (the criterion *is* the metric); `wins()` became `successes()`.
No legacy `int` window format is accepted on load (a clear error is raised): no
committed checkpoint exists, so this is a clean cutover rather than a shim.

## 2. Defect 2 — the 0.10 s ambiguity window was unreachable across control steps

### 2.1 Old behaviour (measured)

`step()` resolved the exchange in the same step as the **first** back trigger
(`resolve_back_events` on that step's triggers only), so a second authentic
trigger 0.02-0.10 s later — 1-5 control steps at 50 Hz, which is the normal case
because the detector needs `confirm_s = 0.30 s` of sustained dorsal contact —
was never observed. The ambiguity rule therefore only ever fired for triggers
confirmed within the *same* step.

```
$ .venv/bin/python <old-code replay>            # HEAD:src/wrestling/env.py grafted back in
OLD code cross-step (gap 0.06 s): winner=a ambiguous=False triggers={'a': None, 'b': 0.32} duration=0.320
OLD code late       (gap 0.20 s): winner=a ambiguous=False triggers={'a': None, 'b': 0.32} duration=0.320
```

The first row is the bug: `a` really does take its back 0.06 s after `b`
(confirmed by a detector-only run, §3 tests), yet the exchange was scored for `a`
with no ambiguity.

### 2.2 New behaviour

When the first back trigger arrives, the exchange is **held open for at most
`AMBIGUITY_WINDOW_S` (0.10 s = 5 control steps)**, simulating normally, and then
resolved with `resolve_back_events` over **all** triggers observed in that
window. It ends early as soon as the *other* robot also triggers. Back
resolution still outranks OOB/timeout/match-clock exactly as before; knees/hands
remain non-terminal; `ExchangeRecord` (including `back_triggers`, `ambiguous`,
`duration`) keeps its meaning.

Measured after the fix (same two scenarios):

| scenario | physical trigger times | result |
|---|---|---|
| near-simultaneous (`a` lands ~0.06 s after `b`) | `b=0.32`, `a=0.38` | `ambiguous=True`, no score, both triggers logged, `duration=0.38` (ended at the **second** trigger) |
| late (`a` lands 0.20 s after `b`) | `b=0.32`, `a=0.52` (detector-only) | `winner="a"`, not ambiguous, `a` never seen, `duration=0.42 = t_b + AMBIGUITY_WINDOW_S` (bounded hold) |

Non-terminal ground states are untouched — verified by the full suite, including
`test_knee_hand_contact_not_terminal_through_rl_wrapper`,
`test_exchange_timeout_draw`, `test_stand_hold_long_timeout_draw`,
`test_oob_forfeit`, `test_match_clock_accounting` (all unchanged and green).

### 2.3 One superseded expectation (updated, not weakened)

`test_sprawl_replay_back_event_scores` asserted `duration == t_b` (the old
"end at the first trigger" behaviour). It now asserts
`duration == t_b + AMBIGUITY_WINDOW_S`, i.e. the held window — a stronger,
step-exact statement of the new contract. Every other assertion in that test
(winner/loser, cause, `t_b >= confirm_s`, `end_back` dorsal, reward, upper bound)
is unchanged.

## 5. Progress-reward finding (documented decision, no behaviour change)

`obs.reference_phase` is a pure function of `exchange_time`, so the reward's
`progress` term (`w * (gamma * phase' - phase)`) is a **command-clock potential**
— identical for a robot that is executing the technique, standing still, or lying
down. It carries **no physical-progress signal** and must not be read as one.
Recorded as a design decision in `src/rl/reward.py`'s term documentation:
keep the term available (the PISTY A-D skeletons still weight it), and **default
`progress` to 0 in motor-curriculum tasks (M1-M4)**, whose progress must be
measured physically (distance/velocity/height/CoM) per
`docs/MOTOR_CURRICULUM.md` §2. No behaviour was changed here — this is the
documented decision plus the requirement on future M-task specs
(`RewardWeights.progress` already defaults to `0.0`).

## 6. Known limitations / next tightening steps (flagged, not solved)

1. `min_similarity = 0.5` (A-C) is a placeholder; it needs a calibrated
   recognition gate from the scorer's held-out evidence (§1.5).
2. The execution criterion needs a *measurement*: with the scorer unavailable (or
   the learner not being the technique's executor) A-C cannot advance — correct
   ("no evidence → no promotion", §3.3) but it must be visible; `gate_status()`
   reports `unmeasured` for that.
3. D's outcome criterion is still satisfiable by a collapsing opponent — that is
   the audited 299/0/20 counterexample, and the reason the
   `success_hook` attribution placeholder exists for D-E. Until the technique
   verdict is wired, D-E gates should be read together with the video/held-out
   evidence required by §3.3.
4. Adjacent latent quirk found while wiring (not fixed, out of scope):
   `StageReward.shaping` scores only when `counter % score_every == 1`, so
   `ScorerAdapter(score_every=1)` silently disables scoring (0 % 1 == 0). The
   default (`scorer_every=5`) is unaffected; the one-line fix is
   `% score_every == 0` with an adjusted counter start.
5. Checkpoint compatibility: a pre-fix checkpoint's `curriculum.window` holds
   ints and its `AdvanceRule` holds `threshold`/`metric`; loading it now fails
   loudly rather than silently mis-gating (no such checkpoint exists in the
   repo).
